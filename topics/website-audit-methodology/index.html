    Технология аудита сайтов («техосмотр сайта») — методология¶

    Статус: боевая, проверена 11-12.08.2026 на bootslab.ru + hardpart.ru (отчёт: /opt/audit-kit/examples/security_report_bootslab_hardpart_152fz.pdf). Проект «Аудит», экономика/статус — topics/audit-project-status.md, роадмап — /root/.hermes/plans/2026-08-11_1700-audit-roadmap.md.

    Что это¶

    Автоматизированный аудит безопасности любых сайтов МСБ (не только магазинов) + обязательная проверка 152-ФЗ (персональные данные) + отчёт PDF на человеческом русском. Ключевое правило Сергея: проверка на утечку/обработку ПДн по 152-ФЗ — основной критерий проверки, отчёт без блока 152-ФЗ = брак.

    Юридические рамки (всегда)¶

    • Сканировать только с письменного согласия владельца (ст. 272 УК). Scope-контракт: /opt/audit-kit/templates/scope.md
    • Режим non-intrusive: доказываем уязвимость, НЕ эксплуатируем. Никаких payload'ов, брутфорса, изменения состояния
    • Лицензия ФСТЭК не нужна на консультационные/аналитические услуги (ИП достаточно); слово «пентест» в оферте не использовать

    Уровни глубины¶

    Уровень Что делаем Статус
    1. Поверхностный CMS-версии, SSL, заголовки, порты, утечки в JS-коде ✅ автоматизировано
    2. Шаблонный Nuclei (9000+ шаблонов), типовые проверки WP/Битрикс ✅ есть гайд
    3. Логика приложения IDOR, авторизация, JWT, «проверка лицензии только если ключ заполнен» 🟡 LLM-анализ
    4. Эксплуатация Реальное проникновение, выгрузка чужих данных ⛔ НЕ делаем

    Инструменты (все MIT/Apache, коммерчески безопасны)¶

    Инструмент Роль Лицензия
    Nuclei (ProjectDiscovery) Ядро: CVE, exposures (.git/.env/phpmyadmin), misconfigs, TLS, headers MIT
    httpx / tlsx Фингерпринт CMS/платформы, TLS-проверки MIT
    OWASP ZAP DAST (spider + passive всегда; active — только с согласием) Apache-2.0
    Nmap (только TCP-скан портов) Открытые порты FTP/SSH/MySQL NPSL — не встраивать
    curl / openssl / dig / whois Разведка, заголовки, TLS, DNS —
    Playwright (HTML→PDF) Генерация отчёта Apache-2.0
    Python (regex-скан форм) Проверка 152-ФЗ: чекбоксы, капча, метрики, политики —

    ⚠️ WPScan — custom-лицензия, нельзя для коммерческого SaaS (только CLI без токена). Nmap — не встраивать в продукт (NPSL). GPL (testssl.sh, sqlmap) — серая зона, держать изолированно.

    Инструмент Версия Что дал в контрольном прогоне
    gau v2.2.4 (lc/gau) MIT 101 URL bootslab / 20 hardpart: llms.txt, .well-known/* (ai-plugin.json, security.txt), ads.txt, старые страницы. Исторические URL → проверка живых (404 = чисто)
    waybackurls v0.1.0 (tomnomnom) MIT 555 URL hardpart: выявлен прошлый CMS — Concrete5 (пути /application/files/, /ccm/, /application/themes/54647/) — сайт переезжал с Concrete5 на WordPress; старые файлы 404 (не дыра, но показывает историю)
    crt.sh API 502 (перегружен) — не критично, subfinder покрывает поддомены
    OWASP ZAP stable (Docker) Apache-2.0 zap-baseline.py (spider + passive scan) — пассивный режим без нагрузки; отчёт HTML+JSON

    Результаты ZAP (12.08.2026, оба сайта): bootslab — 0 FAIL, 13 WARN, 53 PASS; hardpart — 0 FAIL, 14 WARN, 52 PASS. Подтверждены: отсутствие security-заголовков (CSP/HSTS/anti-clickjacking/X-Content-Type-Options), отсутствие Anti-CSRF-токенов, cookies без HttpOnly/SameSite (bootslab), слабый CSP (hardpart: wildcard, unsafe-inline), раскрытие версий (X-Powered-By/Server). Ничего нового сверх ручной проверки+Nuclei — ZAP полезен как независимое подтверждение для отчёта.

    Питфоллы очереди 2: - gau/waybackurls дают много «мусорных» URL (wp-json/oembed, .well-known/, старые пути) — фильтровать: grep -vE "\.(css|png|jpg|svg|woff2?|js)(\?|$)", проверять интересное curl'ом с cookie beget=begetok - Исторические URL ≠ живая дыра: старый CMS (Concrete5 у hardpart) оставил пути в Wayback, но файлы удалены (404) — фиксировать как «переезд CMS, старые пути мертвы», а не как уязвимость - ZAP требует ~4GB диска* (образ 3.7GB) — перед pull чистить /tmp (docker system df, удалять готовые видео из /tmp/triangula-video)

    Установка новых инструментов (рецепт): скачать с GitHub releases (linux_amd64.zip / .tar.gz для ffuf), распаковать python zipfile/tarfile, chmod +x, ln -sf в /usr/local/bin. ffuf распространяется как tar.gz (не zip!). nuclei живёт в /tmp/nuclei-bin/ (или /opt/audit-kit/bin/).

    Питфолл: Beget-анти-бот искажает сканы. Beget отвечает 200 + JS-скрипт установки cookie на ЛЮБОЙ несуществующий путь (adminer.php, admin, backup.sql и т.п.). Все результаты ffuf/nuclei на Beget-хостингах перепроверять с cookie beget=begetok. Реальная картина после cookie: adminer.php=404, admin=302, wp-config защищён (403/405), .git/.env = 405 (закрыты).

    A. Разведка — найти больше «поверхности» (домены, поддомены, старые версии сайта)¶

    Инструмент Лицензия Что даёт Ценность
    subfinder (ProjectDiscovery) MIT Пассивное перечисление поддоменов из 30+ источников (crt.sh, DNSDumpster, Censys и т.д.) 🟢 Высокая — забытые dev/staging-поддомены = отдельная дыра
    httpx -subs (уже есть!) MIT Проверка найденных поддоменов: живые, статусы, заголовки, технологии 🟢 Высокая — вход для nuclei
    dnsx MIT Быстрый DNS-резолв, wildcard-детект 🟡 Средняя
    crt.sh / Censys / Shodan API/бесплатно Транспарентность сертификатов (исторические домены), интернет-сканы (порты, SSL) 🟡 Средняя — пассивно, без нагрузки на цель
    gau / waybackurls MIT Исторические URL из Wayback Machine — старые страницы, параметры, бэкапы 🟢 Высокая — параметры для проверки IDOR/SQLi
    amass Apache-2.0 Глубокий OSINT по доменам 🟡 Средняя — тяжёлый, для наших задач subfinder хватит

    B. Контент-разведка — найти скрытые файлы/директории¶

    Инструмент Лицензия Что даёт Ценность

    waybackurls + ffuf combo MIT Старые URL → проверка живых 🟡 Средняя

    Инструмент Лицензия Что даёт Ценность

    Конвейер проверок (уровни 1-2, ~10-15 мин на сайт)¶

    Подробные команды: скилл web-security-audit → references/audit-checks.md, references/wordpress-audit-checklist.md. Схема:

    1. Разведка: dig (A/CNAME/MX/NS), whois (владелец, хостинг → локализация 152-ФЗ), curl -sI (server, x-powered-by)
    2. Технологии: grep главной по wp-content/bitrix/tilda/next.js/cloudflare
    3. Заголовки безопасности: X-Frame-Options, CSP, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, HSTS (каждый по отдельности)
    4. Служебные файлы: robots.txt, sitemap, security.txt, favicon
    5. Скрытые пути: /.git/config, /.env, /admin, /wp-admin, /phpmyadmin, /backup.zip → все 404
    6. Утечки в клиентском JS: base64-строки, токены, ключи → декодировать (base64 ≠ шифрование!), токен проверять только через getMe
    7. WordPress (если WP): версия ядра (feed generator + wp-links-opml.php + readme.html — 3 источника), плагины/темы из wp-content, REST API /wp-json/wp/v2/users (перечисление логинов), wp-login без rate-limit, xmlrpc.php (405 = хорошо), wp-config бэкапы
    8. Порты: nmap -sT --top-ports 50
    9. Nuclei: -update-templates → exposures/misconfiguration/technologies/cves/wordpress, -silent -rate-limit 20
    10. 152-ФЗ блок (см. ниже)
    11. Отчёт PDF (см. ниже)

    Блок 152-ФЗ — обязательный (главный критерий)¶

    Полная методика: скилл web-security-audit → references/fz152-compliance-checklist.md. Сводно:

    8 требований: (1) политика ПДн + идентификация оператора [30-60 тыс ₽]; (2) согласие на КАЖДОЙ форме [300-700 тыс, повторно 1-1,5 млн]; (3) уведомление РКН/реестр операторов [100-300 тыс]; (4) локализация БД в РФ [1-6 млн]; (5) HTTPS/безопасность; (6) cookie-баннер + метрики до согласия; (7) права субъекта; (8) поручения обработчикам.

    Проверки на сайте (Python regex по HTML): - Ссылки на политику (/privacy-policy/, /politika), упоминания: политик, персональн, согласие, обработк, cookie - Каждую

    отдельно: есть ли input[type=checkbox name=agreement] (data-required) и капча — популярная тема Impreza даёт 3 формы, из них 1 без чекбокса = нарушение - Политика: оператор (ООО/ИП/наименование подставлено!*), цели, состав данных, основания ст.6, отзыв, права, сроки, третьи лица, локализация, реестр РКН - Метрики: ym(, "init") сразу при загрузке = сбор данных ДО нажатия «Хорошо» в cookie-баннере (нарушение)

    Реестр РКН — через российский прокси (с Hetzner не работает): 

    python3 /opt/audit-kit/scripts/check_rkn_registry.py --inn 7743822740   # → «77-22-035780 | ООО "ПРОММЕТ" ...» = найден
python3 /opt/audit-kit/scripts/check_rkn_registry.py --name "Bootslab" # → «НЕ НАЙДЕН» = нарушение/не подтверждено
    Скрипт ходит через 3proxy Яндекс-релей (51.250.74.235:3128, параметры в topics/yandex-relay-proxy.md). Итог в отчёте формулировать по факту: рег. № / «не найден, требуется ИНН владельца».

    Отчёт PDF¶

    • Генерация: HTML → Playwright page.pdf(format='A4', print_background=True) (кириллица из коробки, пример-шаблон: /opt/audit-kit/examples/security_report_template.html)
    • Структура (11 стр., формат одобрен): титул (ресурсы, уровень риска, дата, методология non-destructive, основание) → резюме для руководства (exec + таблица находок №/находка/ресурс/уровень) → методология (метод/инструмент/результат + таблица объектов) → результаты по каждому сайту (карточки findings: бейдж риска + описание + рекомендация) → раздел 152-ФЗ (сводная таблица 8 требований × сайты + нарушения с составами ст. 13.11 + «что уже хорошо») → приоритизированный план P0-P3 (с трудозатратами) → заключение (совокупный риск штрафов, целевой уровень после P0-P2)
    • Обязательно «проверено, не найдено» (показывает объём работы) и «что сделано хорошо»
